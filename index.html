SYSTEM 01

An Equipment Management System across three plants

Lite-On Technology · Guangzhou · 2019–2022 · C#, ASP.NET MVC, Oracle

Machine maintenance at the Guangzhou site ran on paper. To find out which machines were down you walked the floor and read paper forms. Maintenance schedules were on paper too, so maintenance got missed and there was no early warning. Three plants, making car lights, casings and circuit boards. Different product lines, different processes.

The decisions I made

  • One system for all three plants, not three systems. A single Oracle database with a plant dimension separating the product lines. We were a small team: one codebase means one set of fixes rather than three, and one database means the lines are comparable and share the same reports.
  • Hybrid data collection. We read machine signals directly wherever the equipment supported it, and used manual reporting for the rest. Waiting for every machine to become instrumented would have meant shipping nothing.
  • Pilot one plant, then roll out. The processes genuinely differed, so we adjusted per plant and trained the floor staff on the new workflow rather than assuming they would adopt it.
  • Integrated the system with SAP. The EMS pulled ERP data and combined it with machine-status data collected from the equipment.

SYSTEM 03

Delivery platform for a compliance engine

Carnegie Mellon capstone with IRALOGIX · 2026 · five-person team · AWS EKS, Helm, ArgoCD

A regulatory-compliance platform for retirement-account management. I took the delivery and platform side. The team was five people, so what follows is split into what I did and what I did not.

Mine, end to end

  • Packaged the API service as a Helm chart and delivered it to AWS EKS through an ArgoCD Application, GitOps style.
  • Built the self-hosted GitHub Actions runner fleet on EKS with rootless BuildKit, so images build without privileged containers, backed by an ECR registry cache. I proved the GitOps loop rather than assuming it: scaled replicas to watch auto-sync, then added and removed a temporary ConfigMap to watch prune.
  • Implemented Ed25519-signed JWT verification for internal service-to-service calls. It routes by issuer and fails closed with no fallback path. Covered by a 12-test pytest suite.
  • Designed and implemented the observability architecture: the application emits OpenTelemetry only and a Collector selects the backend at deploy time; the backend changed three times in three weeks and the application did not.
  • CIDR-restricted ALB ingress and the cutover from mock auth.
Not mine, and stated because a portfolio that only lists wins is not worth reading

The ArgoCD PreSync hook that applies schema migrations, the IRSA service-account trust setup, and the ArgoCD bootstrap on EKS were teammates' work. The compliance verdict engine, the admin CRUD and the OpenAPI schema were too.

The EKS cluster itself, External Secrets Operator and the AWS Secrets Manager entry already existed. I installed onto that platform; I did not provision it.

SYSTEM 04

Two internal tools, and an honest note about what the AI does

Same capstone · Claude agent skills, Python

A source validator for regulatory rule models

For a given US state, it maps every field of the rule-model schema to a confirmed official source URL plus instructions for finding it on that page. The design is mostly about what it refuses to do: an explicit source-priority chain, unconfirmed fields emitting null and being flagged rather than guessed, and a human review gate before anything is treated as final. The authoritative schema is pulled from Confluence over MCP as the baseline.

A meeting pipeline, Zoom to Confluence

Takes a recording from Zoom through Drive to a correctly parented and labelled Confluence page, packaged as agent skills over a Python package. A sync mode diffs local folders against Confluence by date prefix and publishes only what is missing.
